# GoStyle Booking API — mobile client guide

Everything here was generated by reading the controllers and DTOs, and every
example was executed against a running server. Where a response is shown, that
is the response the server actually returned, not an illustration.

`scripts/verify-docs.mjs` re-runs every `curl` on this page and checks the
status against the one printed beneath it:

```bash
BASE=http://localhost:3099 TOKEN=... node scripts/verify-docs.mjs docs/api/MOBILE.md
```

It exits non-zero if the API and this page have drifted apart. Run it when you
change an endpoint.

- **API version** — all routes are under `/v1`, except `GET /health`.
- **Content type** — `application/json` on every request that has a body.
- **Money** — always integer **minor units** (fils). `AED 1.00` is `100`.
  Fields ending `Minor` are integers; the matching field without the suffix is
  a preformatted display string (`"AED 453.60"`). Never do currency maths on
  the display string.
- **Times** — `startMin` is the **minute of the trading day**, counted from
  midnight local. `600` is 10:00, `1080` is 18:00. The matching `start` field
  is `"HH:MM"` for display.
- **Days** — `YYYY-MM-DD`, always. The regex is enforced server-side.

## 1. Getting started

### Base URL

There is no public base URL committed to this repository. Ask the backend team
for the environment you are pointed at, then:

```bash
export BASE="https://<the-host-you-were-given>"
```

Every example below is `curl -X … "$BASE"/v1/…`.

### Authentication

Every route requires a bearer token **except** these: `GET /health`,
`GET /v1/availability`, `GET /v1/availability/catalogue`, and
`POST /v1/webhooks/payments` (which is signature-guarded instead). The guard is
global — a new route is protected unless somebody deliberately opens it.

```
Authorization: Bearer <token>
```

Two different kinds of token are accepted, and the API tells them apart by
claims **inside the signature**, not by a header:

| Kind | Identified by | Verified | Becomes |
| --- | --- | --- | --- |
| Staff / manager | `iss: "gostyle-api"` | locally, HS256 against `JWT_ACCESS_SECRET` | `staff` or `manager` |
| Customer | `aud: "gostyle-consumer"` | over gRPC against the consumer API | `customer` |

A mobile customer app sends the **customer** token. `roles` on a staff token
decides manager vs staff: `super_admin`, `company_owner` and `branch_manager`
become `manager`; every other role becomes `staff`. That default is deliberate
— a role invented next month inherits the least power, not the most.

A token that is neither is rejected with `401 Unknown token issuer` rather than
being quietly tried as a customer.

### `X-Tenant-Id`

```
X-Tenant-Id: <tenant>
```

Optional. Trimmed, and rejected if empty or longer than 64 characters. It is
**stored on the rows you create and nothing else** — see
[Things that will surprise you](#5-things-that-will-surprise-you). If it is
absent, the `tenantId` claim on a staff token is used instead.

### There is no `X-Branch-Id`

The branch is **a field in the request**, not a header. Most endpoints take
`branchId` (or `branch` on the three older ones) in the body or query, and
several default it to `"marina-walk"`. A staff token also carries a `branchId`
claim, but no endpoint reads a branch from a header. If you have been told to
send `X-Branch-Id`, it is being ignored.

### Validation

The global pipe runs with `whitelist` and `forbidNonWhitelisted`. **Any field
the DTO does not declare is a 400**, listing the offending property:

```json
{
  "message": ["property services should not exist", "serviceIds must be an array"],
  "error": "Bad Request",
  "statusCode": 400
}
```

### Error shapes — there are four

There is no custom exception filter, so bodies are Nest's stock shape. Four
variations reach you, and a client that assumes one will crash on another.

**A. The ordinary error** — `401` `403` `404` `409` `410` `422`. `message` is a
**string**:

```json
{ "message": "No such booking", "error": "Not Found", "statusCode": 404 }
```

**B. A validation failure** — always `400`. `message` is an **array**:

```json
{ "message": ["day must be YYYY-MM-DD", "property foo should not exist"],
  "error": "Bad Request", "statusCode": 400 }
```

**C. `402 Payment Required`** — the one hand-built body, carrying keys no other
error has: `requiredMinor`, `tenderedMinor` and the full `requirement` with its
`trace`. See [surprise 2](#2-a-hold-is-a-countdown-not-a-guarantee).

**D. An unhandled fault** — `{ "statusCode": 500, "message": "Internal server
error" }`, with no `error` key at all.

So: **`typeof body.message` is not stable.** Normalise it — `[].concat(body.message)`
— before showing it, and do not rely on `error` being present.

## 3. Endpoint reference

47 routes. Generated by reading each controller, its DTO classes and the
handler behind it, then verifying against a running server.

**How to read this**

- *Required* means the DTO rejects the request without it. A few fields are
  optional to the validator but required by the domain — the Rules column says
  so where that is true, and the failure is a `422`, not a `400`.
- The `401` rows repeat on nearly every route because the guard is global.
  They are listed once here rather than on every endpoint:

| Status | Message | When |
| --- | --- | --- |
| `401` | `Missing bearer token` | no `Authorization` header, or not `Bearer <token>` |
| `401` | `Malformed token` | the bearer value is not a decodable JWT |
| `401` | `Unknown token issuer` | neither `iss: gostyle-api` nor `aud: gostyle-consumer` |
| `401` | `Token expired` | staff token past `exp` |
| `401` | `Invalid token` | signature check failed, or the consumer API rejected it |
| `401` | `Staff authentication unavailable` | server misconfiguration — `JWT_ACCESS_SECRET` unset |

- Every route also inherits two from the global validation pipe:
  `400 ["property <name> should not exist"]` for an undeclared field, and
  `404` for a path segment that should be a uuid but is not:

```json
{ "message": "No such resource. That path segment is not a resource id, so either the id is wrong or the route does not exist.",
  "error": "Not Found", "statusCode": 404 }
```

That last one is worth knowing: it is what a **typo in a route** looks like.
`GET /v1/bookings/settings` would have hit it if `settings` were matched by
`GET /v1/bookings/:id`, so a 404 with that message means "check the URL", not
"the record is gone".

## 4. Enums

### The case rule

**We accept either case on input, and always return uppercase.**

That is implemented once, by `@WireEnum`, which uppercases the incoming value
before checking it. `TOGETHER`, `together` and `Together` are all accepted and
all stored as the same thing. Responses are shouted by a single translation
layer, so what comes back is always `TOGETHER`.

**Three older endpoints are exceptions and are strict lowercase.** They shipped
before the contract existed and changing them would break live callers:

| Endpoint | Field | Accepts | Returns |
| --- | --- | --- | --- |
| `GET /v1/availability` | `channel` | `desk` \| `online` — **lowercase only** | `"channel": "desk"` — lowercase |
| `POST /v1/holds` | `channel` | `desk` \| `online` — **lowercase only** | — |
| `POST /v1/bookings` | `channel` | `desk` \| `online` — **lowercase only** | — |

Send `DESK` to any of those three and you get a `400`. Everywhere else — the
quote, settings, groups, series, the lifecycle calls — uppercase is correct and
either case is accepted. Note the asymmetry this creates: `GET /v1/bookings/settings`
returns the key `"DESK"`, and `GET /v1/availability` returns `"channel": "desk"`,
for the same concept.

These three also still take **`services`**, not `serviceIds`. Every endpoint
built since takes `serviceIds`.

All of these accept either case.

## 5. Things that will surprise you

Each of these was checked against the running server before it was written
here. Where the original briefing was not quite right, the correction is
called out — believe this page, not the briefing.

### 1. The deposit can be more than half the total. This is correct.

A Gold customer booking a AED 480 colour is asked for **AED 240 now against a
total of AED 453.60**. That is not a rounding fault and not a bug. Two
different bases are in play:

- the **tier discount and VAT** work on the discounted figure;
- the **deposit** is a percentage of the **pre-discount** total.

The real quote, field for field:

| Line | Minor | Display |
| --- | --- | --- |
| Subtotal (net) | `48000` | AED 480.00 |
| Tier discount (Gold, 10%) | `-4800` | −AED 48.00 |
| Discounted subtotal | `43200` | AED 432.00 |
| VAT 5% *(on the discounted subtotal)* | `2160` | AED 21.60 |
| **Total** | `45360` | **AED 453.60** |
| **Deposit due now** *(50% of the pre-discount 480)* | `24000` | **AED 240.00** |
| Due at checkout | `21360` | AED 213.60 |

The response even labels it: the `Due now` line carries
`"note": "on pre-discount total"`. Show that note.

There is a ceiling of **AED 500** on any deposit (`depositCeilingMinor: 50000`
in settings). It does not bind here — 240 is well under it — but it applies to
every requirement, so a large booking's deposit stops climbing at 500. Three
colour services together:

| Line | Display |
| --- | --- |
| Subtotal | AED 2050.00 |
| Total | AED 1937.25 |
| Deposit — 50% would be AED 1025.00 | **AED 500.00** |

When the ceiling bites, the response says so:

```json
"requirement": {
  "kind": "DEPOSIT",
  "source": "Service rule 50% (Full color and gloss)",
  "clampNote": "capped at the branch ceiling",
  "trace": [ ... ]
}
```

`clampNote` is **absent** when nothing was capped, so check for the key rather
than expecting it. Show it when it is there — "we only take AED 500 up front"
is a good thing to tell a customer.

**Do not file this as a bug.**

### 2. A hold is a countdown, not a guarantee

`POST /v1/holds` gives you **15 minutes** (`expiresInSeconds: 900`, and a
preformatted `countdown: "15:00"`). A **walk-in seat hold is only 5 minutes** —
read `expiresInSeconds` rather than assuming.

Confirming does **not** re-run the availability engine. It locks the hold row
(`WHERE expires_at > now() FOR UPDATE`) and turns its existing reservations
into a booking. What can fail is therefore the hold itself, not a re-plan —
but that is enough to mean a hold is not a guarantee:

Two failures to handle, and they mean different things:

| Status | Meaning | What to do |
| --- | --- | --- |
| `410 Gone` | the hold is dead — expired, or never existed | re-fetch availability and start again |
| `409 Conflict` | the hold was fine, the world moved | re-fetch availability; offers have refreshed |

Real messages:

> `410` — *"This hold expired. Money is never taken against a dead hold.
> Re-check availability before continuing."*
>
> `409` — *"Someone took this while you were paying. Nothing was charged.
> Offers have refreshed."*

Both say *nothing was charged*, because that is the customer's actual question.

**Group confirm is the exception**: `POST /v1/groups/:id/confirm` genuinely does
re-run the plan on fresh masks, because a party is a much bigger claim on the
diary. It can therefore fail for reasons a single confirm cannot.

#### And a third outcome you must handle: `402`

If the booking needs a deposit and you tendered nothing, confirm answers `402
Payment Required` — **not** an error you should treat as a failure, but the
API asking for money. It hands you everything needed to ask for it:

```json
{
  "statusCode": 402,
  "error": "Payment Required",
  "message": "AED 240.00 is required before this booking can be confirmed.",
  "requiredMinor": 24000,
  "tenderedMinor": 0,
  "requirement": { "kind": "DEPOSIT", "source": "Service rule 50% (Full color and gloss)",
                   "trace": [ ... ] }
}
```

The hold is still alive. Take the payment, then confirm again with the same
hold — do not send the customer back to availability.

### 3. Two "accept"-shaped calls return a hold. The third returns bookings.

It is tempting to assume every "take this slot" call behaves the same way.
Two of them do; the group one does not:

| Call | Returns | Then what |
| --- | --- | --- |
| `POST /v1/walk-ins/:id/seat` | a **hold** | confirm through `POST /v1/bookings` |
| `POST /v1/waitlist/:id/accept` | a **hold** | confirm through `POST /v1/bookings` |
| `POST /v1/groups/:id/confirm` | **bookings** — one per participant | nothing; it is already done |

There is no "group accept" endpoint at all. The party hold comes from
`POST /v1/groups/holds`, and `POST /v1/groups/:id/confirm` turns it into
bookings directly.

The waitlist response spells it out itself:

```json
{ "holdId": "3a55c484-…", "start": "11:00", "end": "11:45",
  "expiresInSeconds": 900,
  "note": "Confirm this hold through POST /v1/bookings. The requirement is resolved fresh, so a deposit may be due." }
```

So **there is not one confirm path — there are two.** Singles, walk-ins and
waitlist accepts all funnel through `POST /v1/bookings`. Groups have their own,
`POST /v1/groups/:id/confirm`, which writes one booking per participant and
returns them. Build for both.

Note also that last sentence of the waitlist note: the deposit requirement is
worked out **fresh at confirm time**, so a slot the customer was quoted for
free yesterday can ask for money today.

### 4. `X-Tenant-Id` is stored, not enforced. It is not security.

Verified live: a booking created with no tenant header was read back in full
using `X-Tenant-Id: some-other-salon-group`. Everything came back — code,
status, times.

Nothing filters on `tenant_id`. The column is being populated first so it can
be backfilled and verified before anything depends on it; a filter added before
every row carries a value would silently hide the rows written without one.

Two consequences for you:

- **Never treat the tenant header as an access-control boundary.** It is not
  one, and building UI that assumes it is will be wrong when it becomes one.
- **If you do not send the header, the column is `NULL`.** There is no fallback
  to the `tenantId` claim on the token, despite a comment in the schema that
  says otherwise. Send it on every request if you want the rows attributed.
- A malformed header — empty, whitespace, or longer than 64 characters — is
  treated as absent and stores `NULL`. It never errors.

`GET /v1/bookings/:id` echoes the stored value back as `tenantId`, so you can
see what was recorded even though nothing gates on it.

### 5. Grain follows the channel: 5 minutes at the desk, 15 online

`DESK` offers start times every **5** minutes; `ONLINE` every **15**. The
channel also sets the minimum lead time — 15 minutes at the desk, 60 online.
Both come back in `GET /v1/bookings/settings`:

```json
"channels": {
  "DESK":   { "grainMin": 5,  "leadMin": 15 },
  "ONLINE": { "grainMin": 15, "leadMin": 60 }
}
```

The availability response echoes the `grainMin` it used, so you never have to
infer it. Do not hard-code either number — read settings.

### 6. Refusals are written for the operator. Show them verbatim.

Domain refusals carry a reason and, where one exists, a remedy. They reach you
in **two different shapes**, depending on whether the refusal is an error or an
answer.

**As an error** (`409`, `410`, `422`) the two are joined into one `message`
string:

> *"No arrangement of professionals covers the whole party at this time. Try
> another time, or switch to finish-together."*
>
> *"10:05 is no longer available. Offers have refreshed."*

**As a successful answer that happens to be "no"** — `POST /v1/bookings/availability/group`
returns `200` with `feasible: false` — they are **separate top-level fields**:

```json
{
  "feasible": false,
  "lanes": [],
  "reason": "Nobody available covers B's services at this time.",
  "remedy": "Change that service, or try another time."
}
```

Concatenate them yourself for display. The remedy is situational, not a
constant: ask for a specific professional and the same refusal comes back with
*"Relax the professional preference, or try another time."* instead.

Refusal **lists** carry a per-item `reason` too — `GET /v1/bookings/eligible-staff`
returns a `refused` array where every entry explains itself:

```json
{ "id": "reem", "name": "Reem S.",
  "reason": "does not hold the required skills: color" }
```

`POST /v1/bookings`'s `402` is the same idea in a richer shape: a sentence for
the customer (*"AED 240.00 is required before this booking can be confirmed."*)
plus the machine-readable `requiredMinor` and the full requirement trace.

**One exception, and it matters:** `400` validation errors are *not* written
for humans. They are class-validator strings in an array
(`["serviceIds must be an array"]`). Those are for you, not for the customer.
Everything else — `409`, `410`, `422`, and the `reason` fields — is written to
be read aloud at a desk.

**`fired: true` does not mean "this rung set the price."** More than one rung
can fire, and the **strictest one wins**. The rung that actually decided the
amount is named in `source` — here, `"Service rule 50% (Full color and gloss)"`
— which is also returned at the top level as `requirementSource`. If you render
the trace, mark the winner from `source`, not from `fired`.

Show `source` by default; put `trace` behind a "why?" affordance.

The rungs come back in evaluation order, which is why `4b` sorts after `6` —
peak escalation is applied last, and it does not produce an amount of its own.
It takes whatever the other rungs settled on and moves it up one level: no
deposit becomes a deposit, a deposit becomes payment in full. Do not re-sort
the array by name.
